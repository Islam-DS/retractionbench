# Retraction Watch / PubMed metadata traps

A short, citable table of every data-quality trap this project's Phase 5 audit actually hit,
each one caught by a concrete failure (a crash, an anomalous count, a sanity check), not
anticipated in advance. Intended for the paper's Methods or Limitations section, or as a
standalone caveat for anyone else building on this corpus or on Retraction Watch directly.
Every row cites the exact field, the real count in the live data, and how it was caught.

| # | Field | Trap | Real prevalence | How it was caught |
|---|---|---|---|---|
| 1 | `original_paper_pubmed_id` | Literal string `"0"` used as a "no PubMed ID" placeholder, not a real PMID or an empty value | 32,844 / 66,203 rows with a non-empty value (49.6%) | A sample drawn without excluding it was 48% unresolvable PubMed lookups |
| 2 | `original_paper_doi` | Literal strings `"unavailable"` / `"Unavailable"` used as placeholders | 518 / 33,118 non-null values in the Retraction-nature-filtered population | A DOI-shaped lookup to Crossref/OpenAlex 404'd on the literal string |
| 3 | `retraction_pubmed_id` | Same `"0"` placeholder convention as field 1, in the separate notice-PMID field | 1,698 / 33,230 non-null values | Found by applying the same validator to this field after catching trap 1 |
| 4 | `retraction_date` | `"1/1/1970 0:00"` (the Unix epoch) used as a placeholder date | 6 rows (negligible at this population size, but present) | Checked directly after noticing `1970` as a `MIN(retraction_date)` |
| 5 | `record_id` (candidate-pool export, this project's own pipeline, not RW itself) | The same RW record exported once per domain-specific MeSH query it matched, producing duplicate rows for one real paper | 68 / 364 rows (3 papers duplicated in a 24-case gap subset; 64 papers duplicated in the full 296-paper pool) | Already caught once, 2026-08-10 (ADR-066) -- re-discovered this round because the correction had never been synced into the manuscript's prose, only into the underlying results files |
| 6 | `original_paper_pubmed_id` | The same real PMID can be entered on multiple distinct RW records (a genuine RW data issue, not an export artifact) | 1,537 distinct PMIDs duplicated (3,454 rows) in the full population; one extreme case, PMID 35073579, appears 281 times across 281 otherwise-distinct Expression-of-Concern records, all dated the same day -- a clear bulk-entry error, not organic duplication | Found while computing a routine duplicate-PMID check before sampling |
| 7 | `retraction_nature` | Not every RW record is a retraction -- `"Correction"`, `"Expression of concern"`, and `"Reinstatement"` also appear, and checking one of these for a missing `Retracted Publication` PubMed tag is the wrong check (that tag was never expected on it) | 3,837 / 33,359 rows with a real PMID (11.5%) are non-Retraction nature | A sampling frame drawn without this filter silently mixed the wrong population into a "PubMed retraction-tagging" audit |
| 8 | PubMed `pubtype` | Two distinct, easily-confused tags exist: `"Retracted Publication"` (goes on the *original* article) and `"Retraction of Publication"` (goes on the *notice's own* record). If a source's "original paper PMID" field actually points to a notice, checking it for the first tag will always look like a gap | Checked across both Phase 5 samples: 0/24 curated-pool cases, 0/300 broad-sample cases | Added as an explicit per-case check this round rather than assumed absent; unit-tested directly (`tests/test_phase5_part_b_scaled_check.py`) |
| 9 | OpenAlex `is_retracted` | Sourced directly from Retraction Watch (OpenAlex's own documentation), not an independent signal -- using it to "corroborate" an RW claim is circular | Affects every OpenAlex-based check in this audit | Caught by reading OpenAlex's own API documentation, not by a code bug |
| 10 | Crossref `relation` | A non-empty `relation` field is not necessarily about retraction -- unrelated relation types (e.g. `"has-review"`) exist and must be filtered on key name, not just presence | 1 confirmed false positive in this audit (PMID 30688986) | Found by inspecting the raw JSON of a "corroborated" case rather than trusting a boolean check |
| 11 | Crossref `update-to` | Carries a `source` field distinguishing publisher-deposited (`"publisher"`, independent) from Retraction-Watch-derived (`"retraction-watch"`, not independent) updates -- both look identical if this field is ignored | Affects every Crossref-`update-to`-based check | Found by reading Crossref's own documentation on Retraction Watch integration |
| 12 | `original_paper_pubmed_id` / `retraction_pubmed_id` | A PMID can be flatly **wrong** -- not a placeholder, not a notice/original mix-up, but a different real article entirely, apparently via a dropped trailing digit. Checking PubMed's tag status on the wrong PMID produces a false gap even though the *real* article is correctly tagged | 1 confirmed case in the Part B broad sample (RW record_id 250: both PMID fields are truncated by one digit relative to the real PMIDs 18349203/19299812) | Caught by a title mismatch between RW's own `title` field and the PubMed record actually returned at that PMID, then confirmed by searching PubMed for RW's title text directly (`results/phase5_part_b_downstream_dossiers.md`) |
| 13 | PubMed `CommentsCorrectionsList` (`Update in`/`Update of`) chains, specifically for Cochrane Database of Systematic Reviews entries | A Cochrane review's formal "WITHDRAWN:"/retraction signal frequently lands on a *later* PMID in its own pub-version chain (`pub2` -> `pub3` -> ...) than the specific pub-version PMID a source's "original paper" field references. Checking only that exact PMID's own `pubtype` misses independent corroboration that is one or more hops away in PubMed's own structured cross-reference field -- **but that corroboration confirms a withdrawal event, not necessarily a data-integrity reason**: 3 of the 4 Cochrane cases resolved this way state a purely administrative reason (timeline, consolidation, splitting) in the notice's own text, not fraud/error/misconduct language | 5/12 of Part B v2's `rw_derived_only` cases were Cochrane or Cochrane-adjacent entries resolvable this way | Found by following `CommentsCorrectionsList` entries live rather than trusting the absence of a same-PMID tag; reasons found by reading each notice's own stated text, not just its title/pubtype (`results/phase5_part_b_downstream_dossiers.md`) |
| 14 | `title` (RW) vs. PubMed's own title at the same PMID | A systematic check across both Phase 5 populations (296 curated-pool + 300 broad-sample distinct PMIDs, `scripts/phase5_title_mismatch_check.py`) for titles that do not reasonably match, beyond the one wrong-PMID case (trap 12) already known, found: 2 PMIDs that do not resolve in PubMed at all (both already disclosed/excluded elsewhere -- one as a known "pending manual check" exclusion from the curated pool, one as Part B's own 1 unresolved-lookup case); 1 case where a single PMID represents an entire conference-abstract-proceedings volume rather than one specific abstract, so RW's per-abstract title does not match PubMed's generic proceedings title even though the tag-check itself still returns a valid, correct result; 1 false positive from the similarity heuristic itself (a foreign-language article whose PubMed title is a full German original and RW's title a partial English paraphrase -- same paper, confirmed by subject match) | 5/596 titles flagged below a 0.4 normalized-similarity threshold; 0 further wrong-PMID cases beyond the one already found | Built as a systematic, reusable, tested check (`tests/test_phase5_title_mismatch_check.py`) after the one wrong-PMID case (trap 12) was found by chance during the Part B dossier re-check, specifically to check whether that was an isolated incident |

**General lesson, stated once rather than per-row:** every one of these traps is a case where a
field looked populated and well-formed enough to use without a second check, and wasn't. None
were caught by inspecting the schema or documentation in advance -- all were caught by a
concrete, surprising downstream failure (a crash, an anomalous count, a cross-source
disagreement) and then traced back. A data-validation pass
(`src/retraction_bench/ingest/rw_data_quality.py`, run before every audit script that touches
this table) now encodes checks 1-4, 6, and 7 as reusable, tested functions; check 8 is
unit-tested separately (`tests/test_phase5_part_b_scaled_check.py`, since it is logic internal to
`scripts/phase5_part_b_scaled_check.py`'s `_parse_pubmed`, not the shared validation module);
check 14 is unit-tested separately (`tests/test_phase5_title_mismatch_check.py`) and runnable at
scale (`scripts/phase5_title_mismatch_check.py`); checks 9-13 are per-case/per-field logic
applied manually in dossier-level audits, not yet generalized into an automated, reusable check.
